## 范围与证据规则

- 来源 saltnya、brokestar233、masson 均保留在用户指定的 Libs 目录；所有整合修改只在本项目内进行。
- saltnya 的完整 Forge 内容作为初始基础和功能保留基准。逐系统选择实现；不把开发时间当作质量证据。
- 一份共享领域逻辑，一套稳定的材料/注册 ID 和配方语义；Forge 与 NeoForge 只保留必要的生命周期、注册、网络、能力、存储、渲染接口差异。
- 第一条完整玩法链暂定为取得铜锡原料 → 处理材料 → 固体燃烧箱供热 → 坩埚熔炼/合金 → 模具铸出青铜 → 制作并使用青铜工具。实施前依据现有代码及配方逐步核实其生存可达性。
- 代码存在、静态检查、编译、开发环境启动、成品 jar 启动、玩法、真实世界保存并重载是不同等级的证据。未跑的检查始终标记为未验证。
- 项目旧文档的完成百分比与发布声明只能作为调查线索，不作为本项目验收结果。

## 阶段及退出条件

### P0 — 完整性、来源与可重复基线

产出：三源逐文件 SHA-256 清单、源码/资源/测试统计、许可证与署名清单、缺失依赖列表、逐系统代码差异、本地 Git 快照和基线构建日志。

退出条件：明确哪些源码/历史/第三方依赖可获得；未决授权逐项记录；在整合目录复现项目1构建；形成有源代码证据的实现选择。许可证未决不得通过发布门禁，但可以继续本地核查和开发。

### P1 — 双版本构建入口与共享核心接线

产出：Java 17 的 `core` 领域模块，保留项目1完整 Forge 内容，建立 1.21.1 NeoForge 平台模块；固定依赖版本、可移植构建脚本和双版本 CI。

退出条件：两条构建各自产出可加载 jar，共享核心实际被两平台调用，两个 jar 的注册 ID 无重复，各平台的专用服务器和客户端成功启动。有启动骨架不等于完整功能支持。

### P2 — 第一条完整玩法链与世界持久化

按材料身份/物质量单位 → 配方与合金 → 热量/机器状态 → 游戏交互 → 客户端呈现的依赖顺序迁移。先比较三家纯逻辑和现有回归样本，再作选择；不整体复制第二套材料目录或注册框架。

退出条件：P0 所定生存链在两个版本均可从真实可得原料完成；热量、合金产率、物品/流体守恒和工具损耗一致；专服与客户端联机验证；关服保存后重新启动，所有相关机器状态/材料/物品/进度可恢复。必须记录成品 jar 的测试，NBT 方法往返不代替真实世界重载。

### P3 — 按依赖整合系统

依次处理材料与前缀/统一规则、配方及脚本扩展、机器与多方块、能源、物流、世界生成、渲染与界面、JEI/Jade 等可选集成。系统之间允许在无文件域/底层依赖冲突时并行。

每个系统退出条件：两版本对应玩法验证；项目1已有功能有保留或经过明示的替代决策；新增底层由两平台共享；配方无悬空引用、注册无冲突；客户端类不污染专服；存档与重载实证。删减或延后项进入缺口账本，不能隐去。

### P4 — 回归、迁移与可测试发布

产出：双版本测试 jar、校验和、开发/协作/测试/发布文档、来源与贡献记录、兼容矩阵、已知问题。

退出条件：约定系统范围全数达到相应验收，双版本的构建/客户端/专服/玩法/世界重载证据齐全；许可证和第三方署名落实；原项目存档的支持范围有备份样本实测，失败范围明确；发布 CI 只发布已通过的构建。没有远程归属时只建立本地 Git 和 CI 文件，不猜测 GitHub 所有者。
