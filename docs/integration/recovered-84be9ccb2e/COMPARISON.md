# 系统比较与初步选择

更新：2026-09-30。依据三份只读源码审计。下述是实现候选与阶段安排，不是三源运行质量排名；类数、资源数、覆盖百分比和历史日志都不作为本项目完成证明。采用决定仍须有行为证据。

## 统一结构

初始保留项目1完整 Forge 内容，逐步把可证明不依赖 Minecraft/loader 的规则抽到 Java 17 `core`，Forge 与 NeoForge 消费同一个核心。版本层承载注册、ItemStack/FluidStack、NBT/组件、capability、网络、世界与客户端交互。项目2 Stonecutter 方案是可比较的双版本实现证据；本项目不整体复制其第二套材料/RecipeMap 运行时。项目3 NeoForge 启动方式可借鉴，不能把其注册矩阵直接加入项目1。

进入 NeoForge 的功能逐条记迁入清单。NeoForge 启动骨架或少量演示内容不等于双版本功能一致。每个域需要登记项目1已有内容的保留、替代、延后和缺口。

## 材料与身份

- 项目1有统一材料注册、ID/名字/别名及 DEFINITIONS→LINKS→READY 状态，可作为保留身份的初始基础；多数材料对象仍耦合 Minecraft。
- 项目2有纯 Java MT/OP 数据、MaterialRegistry/MaterialGraph、合金引用与现代prefix×material注册；其 first-wins/snake_case ID 规则不能直接替换项目1身份。
- 项目3有Codec材料定义、运行修订号、来源资格与1.21组件，可吸收数据核查与配置握手方法。

初步选择：保留项目1材料身份和玩家内容，抽出数据定义/物质量/纯条件；把其他两家完善的字段和图关系转为同一个模型。门禁是材料ID/别名清单、组成/合金和单位样例一致，重复注册必须报错或进入有理由的取舍记录，不能静默 first-wins 吞掉来源内容。

## 配方与脚本

- 项目1 RecipeMap 已有索引、冲突检查、动态配方，以及真实reload/网络round-trip测试实现。
- 项目2有广泛静态stock、动态map及datapack/KubeJS seam，但datapack客户端同步明确未完成，SHARPENING原始工具头仍有死端；不能因map/GUI存在就标记玩法完成。
- 项目3有compact lookup、来源编译/分母政策与recipe provenance；其覆盖百分比与零创造可达性是分开的。

初步选择：保持项目1配方身份与消费/产物语义，优先验证其reload与同步，再吸收可证明缺失的stock和来源核查。门禁包含物品/流体引用可解析、输入重复冲突、reload撤销、专服客户端查看器同步、合成链从真实可得材料可达。脚本注册不能引入第二个全局材料目录。

## 坩埚、机器与热学

- 项目1统一基本机器具有耗能、库存/罐、侧IO、cover、进度与NBT；坩埚已有热学/相变/合金/熔毁。
- 项目2纯 Java CruciblePhysics 与单/大型坩埚共享参数，适合比较热学内核；基本机器真实tick与供能存在。
- 项目3的CrucibleThermalModel、MoltenTransferMath与EnergyPackets是纯逻辑候选；MachineTransaction/ExecutionPlan可用于检查加工原子性。其CrucibleProcessCore虽然名为core，实际仍引用MC/NeoForge，不能原样复制进纯Java模块。

初步选择：项目1完整玩法保留，先抽现有行为合约，再对三家热物理、相变顺序、批次产率及输出阻塞作案例比较。特别核对GT6一锭648,648,000 U与项目3一锭144单位，不能因显示为mB而降低全局精度。门禁包括守恒、余量、欠功率暂停、满输出不消耗、爆炸/酸/未知材料边界和真实保存重启。

## 能源

- 项目1已有GT多类型 packet接口、线缆和蒸汽链GameTest；EnergyCompat的IC2/RF路径仍为恒零stub。
- 项目2有MC独立EnergyGate/EnergyBridge、整包FE桥接与两平台capability，适合弥补外部能源面。
- 项目3有signed strength×count、溢出安全、每tick预算和KU/RU区分，适合数值边界比较。

初步选择：同一能量类型、包与热单位契约；外部能力放平台适配。需验证模拟不改状态、真实收/发与整包余量、电压/电流/损耗、过压、交变/转速方向、每tick限额、溢出和物理供热/供汽，不只用debug能量源证明机器能tick。

## 物流与存储

三家均有实际物品/流体管和物流核心，项目1旧文档中的“核心占位”已被当前代码推翻。项目2有迭代路由与多类型cover；项目3有simulate/commit、有限工作预算与比例传输。

初步选择：沿用项目1身份和网络行为基准，比较循环/多出口/速率/过滤/所有权与原子传输边界后吸收完善算法，保持一个网络底层。门禁涵盖不复制/丢失物品或流体、区块卸载/重载、侧IO、所有权/过滤、管网与机器状态的磁盘往返。

## 世界生成

项目1已采用OreBlock宿主/破损BlockState并有旧BE tag迁移，旧“每矿一BE”性能说明已过时。项目2具有origin-seed分片、负坐标/跨区块一致方案、地层和深层矿脉；项目3有固定上游参数、石层/泉矿mutex与布局测试。

初步选择：一个worldgen注册及配置方案，先核对项目1矿物/宿主/掉落和首条玩法材料分布，再比较确定性/跨边界/维度方案。门禁在新世界和新区块验证分布、负坐标、矿石处理、掉落/名称/贴图；不要把三家矿脉全部注册叠加。旧世界生成兼容需单独设计。

## 渲染与界面

项目1有baked model/BE render、机器界面、cover显示与JEI；common menu位于名为client的包，不应凭包名一刀切隔离。项目2强调不可变render snapshot和quad缓存，有ModularUI/JEI/EMI素材来源清单，但缺fork且nojade recipe页已知崩溃。项目3有坩埚液面/几何、机器/仓储界面与Jade/EMI投影。

初步选择：保留项目1现有交互，抽权威状态与presentation projection边界，吸收通过视觉QA的几何/布局。先做到两腿界面、液面、工具交互和查看器同步，再选GUI框架。暂不引入缺源码/版本的ModularUI；amazawa资产须保留其专门授权。门禁是实际客户端操作/截图、专服无client类加载，以及可选mod拔除与组合验证。

## 第一条玩法链与完成门

`PLAN.md` 的起始链为铜锡原料→燃烧箱供热→坩埚熔炼合金→模具青铜→制作/使用青铜工具，逐步扩展蒸汽→加工→物流。已有单环节测试不能取代全流程。两版本须分别在可得资源下完成、做真实客户端/专服交互，再保存关闭进程并重开同一世界。

旧存档不作未经证据的兼容承诺。项目1现有ID/NBT应优先保留；项目2明确无1.7世界迁移，项目3明确旧beta/rc无DataFixer/不支持升级。跨来源世界及1.20.1→1.21.1升级都需要旧ID映射、备份世界和真实迁移测试。
